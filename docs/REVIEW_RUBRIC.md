# EC4 review rubric

This is a project quality rubric, not an admissions scoring model or a statement of any university's requirements.

| Dimension | Review question | Strong evidence | Insufficient substitute |
| --- | --- | --- | --- |
| Intellectual focus | What specific uncertainty does this project investigate? | A bounded question tied to a located observation | A list of impressive technologies |
| Personal agency | What did the student decide or produce? | Dated originals, change explanations, student verification | AI-authored prose or repository ownership |
| Method | Could someone repeat the comparison? | Unit of analysis, inclusion rules, codebook, missing-data treatment | Informal rankings without a denominator |
| Reasoning | Why does the evidence support the conclusion? | Claim–evidence–warrant chain plus rival explanation | Marketing language treated as measurement |
| Technical depth | Which system constraints matter? | Data flow, trust boundaries, failure cases, testable trade-offs | Unverified implementation details |
| Validation | What could disprove the conclusion? | Negative cases, uncertainty, independent checks | Only favorable examples |
| Impact | What changed, for whom, and how is it measured? | Before/after definition with actual records | Assumed reach, intention, or attendance |
| Reflection | How did the student's view change? | Specific initial belief, contradiction, revised view | Generic statements about inspiration |
| Communication | Can a reviewer inspect evidence quickly? | Concise summary, navigable artifacts, exact locators | Volume of files or commits |

## Review sequence

Read the source inventory first. Then inspect each claim's evidence and counterargument. Review project quality independently from the student's verified contribution. Only then draft a short activity description using facts that survive both checks.
