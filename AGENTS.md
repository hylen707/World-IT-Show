# Project documentation workflow

## README as the current research overview

Keep README.md synchronized with the research, rather than treating it as a one-time landing page. When changing source intake, the evidence ledger, methods, analytical code, generated results, or validation, review the README in the same change.

Update it whenever a change affects the research question, the specific contribution, a reported finding or count, the completed stages, reproduction commands, known limitations, or the next unresolved question. A review may conclude that no wording needs to change; do not manufacture a documentation diff.

## Evidence and presentation

Lead with the engineering problem and the evidence-backed contribution. Connect the starting material, decisions, analysis, results, and remaining questions in a coherent project narrative. Use precise, professional language and keep administrative planning and tool-use commentary outside the README.

Keep observations, analytical assumptions, measured outcomes, and proposed work distinct. Do not turn simulated output into product performance, a document title into participation evidence, or repository work into an unsupported personal achievement. Preserve factual attribution and source/provenance records when improving presentation.

## Review before publishing

- Check each reported number and count against the current ledger or generated output.
- Check local links, cited result locations, and executable reproduction commands.
- Reflect substantive changed conclusions and unresolved questions in the README.
- Keep technical changes reviewable and commit messages descriptive of the actual work.

## Project writing

Describe the research subject, methods, evidence, results, and limitations directly. Omit commentary about drafting processes, preparation tools, or outside writing support unless explicitly requested or required by the destination's rules. Keep source citations and factual contribution boundaries accurate; do not infer independent authorship from an omission.

For authorized routine editorial changes, update the existing branch directly without opening a pull request. Use a concise commit message describing the resulting documentation. Avoid adding administrative cleanup narratives to project documents.
